# Пользователи, отдельные базы и переносимый профиль настроек

11 сентября 2026. Первая реализация второго этапа; архив для пилотного обновления.
Это набор изменённых файлов поверх текущего Nexus 2.7.5 с предыдущими исправлениями,
а не полный дистрибутив. Рабочий VPS и GitHub автоматически не изменялись.

## Что реализовано

- Раздел **Пользователи и доступ** (`/access`): создание сотрудников с собственным
  логином/паролем, назначение прав, смена пароля владельцем, блокировка и отзыв доступа.
- Один пользователь может работать в нескольких разрешённых пространствах.
  Для общей базы назначайте сотруднику пространство **Основное**.
- Владелец может создать пустое пространство с собственной SQLite-базой, затем
  назначить туда пользователя. Клиенты, узлы, настройки и ключи не копируются.
- Основное пространство продолжает использовать существующий `data/app.db`.
  Новые: `data/workspaces/<случайный ID>/app.db`. Учётные записи, права и ключи
  пространств находятся в общей `data/control.db`.
- Для каждой дополнительной базы запускается отдельный процесс Node внутри
  той же установки. Поэтому база, кэши, очереди и фоновые циклы не переключаются
  через общую переменную. Это отличается от ранее предложенного рефакторинга
  всех функций в один процесс с контекстами.
- Сервер проверяет разрешение каждого административного запроса. Неизвестные
  маршруты не получают разрешение автоматически. Изменение прав/пароля или
  блокировка немедленно делает прежние сессии недействительными.
- Формы связаны с пространством, в котором открыты. После переключения в другой
  вкладке сохранение старой формы получает 409 и требует обновить страницу.
- Публичные ссылки Основного не меняются. Новые пространства используют
  `/s/<ID>/json/<slug>`, `/s/<ID>/sub/<slug>` и соответствующие страницы подписок.
  Установщик учитывает новый путь при отдельном адресе/порте подписок.
- Повтор запуска пространства после сбоя сохраняет его каталог и ключ.

## Права этой версии

Наборы «Просмотр», «Оператор» и «Администратор пространства» заполняют галочки;
их можно изменить отдельно:

| Разрешение | Действия |
|---|---|
| Клиенты: просмотр | Список, статистика, UUID и ссылки подписок |
| Изменение клиентов | Создание, редактирование, сроки, лимиты, устройства |
| Удаление | Удаление клиента |
| Массовые операции | Массовая синхронизация и перенос клиентов; массовое удаление дополнительно требует права удаления |
| Узлы | Настройка узлов и автовыбора своей базы |
| Маршрутизация | Маршрутизация своей базы |
| Профиль настроек | Переключатели, интервалы, название VPN и значения для новых клиентов своей базы |

Просмотр и доступ к подпискам пока объединены: **не выдавайте право просмотра,
если сотруднику нельзя видеть ссылки/UUID**. Создание и редактирование также
объединены. Это менее дробная модель, чем в первоначальном проекте.

Только главный администратор управляет учётными записями. Его нельзя заблокировать
или понизить через форму сотрудников. Системные настройки, полный web-backup,
SSH/VPN-инструменты, обновления, сертификаты, диагностика и Telegram доступны
только владельцу из Основного пространства. Telegram в дополнительных
пространствах в этой версии ещё не предоставляется.

Кнопки некоторых старых экранов пока не скрываются по правам: запрещённая операция
всё равно блокируется сервером. Самостоятельная смена пароля сотрудником,
принудительная смена при первом входе и полный аудит всех клиентских операций
не включены. Журнал сейчас фиксирует управление пользователями/пространствами
и изменение профиля настроек.

## Профиль только настроек

Раздел **Профиль настроек** (`/preferences`, также доступен через «Ещё»):

1. Задайте значения для новых клиентов: дни, трафик, IP, устройства,
   начало срока после активации. Они заполняют форму создания клиента.
2. В раскрывающемся блоке можно изменить поддерживаемые переключатели и интервалы.
3. Нажмите **Скачать профиль настроек**. Получится файл `.nxpreferences`.
4. В другой установке загрузите файл, проверьте список «было → станет», подтвердите.

Перед применением сохраняется предыдущий переносимый профиль. После импорта
его можно скачать по ссылке в результате и загрузить тем же способом для отката.
Снимки хранятся в `data[/workspaces/<ID>]/backups/`.

В профиль НЕ входят: название VPN, пользователи панели и права, узлы, клиенты,
UUID, ссылки, пароли, токены, домены, IP, маршруты/привязки к конкретным узлам.
Переносятся только разрешённые числовые/перечислимые настройки. Неизвестные
параметры отвергаются, а не исполняются. Старый полный перенос `.nxsettings` —
другой формат, для передачи знакомому этот новый профиль безопаснее.

**«Параметры клиентов» здесь — значения по умолчанию, а не индивидуальные сроки,
лимиты и данные существующих клиентов.** Существующие клиенты при импорте
не изменяются. Название VPN другой установки также остаётся её собственным.
Файл не зашифрован: экспортируемый состав специально не включает секреты.

## Как обновить

1. Сначала сделайте полный backup: `agg` → **5 — Создать резервную копию**.
   Скопируйте архив с VPS. Сохраните `.env`, особенно `APP_SECRET` и `SESSION_SECRET`.
   Базы внешних/локальных 3x-ui и Remnawave резервируются отдельно.
2. Сначала испытайте обновление на отдельном тестовом экземпляре. Если используете
   копию рабочей базы, не давайте ей выполнять синхронизацию с рабочими узлами.
3. Замените файлы из ZIP в корне своего репозитория, сохраняя вложенные каталоги.
   Затем на сервере `agg` → **2 — Обновить проект, сохранив данные**.
   В дополнительных панелях выберите **0 — оставить как есть**.
   Не выбирайте переустановку/удаление и не меняйте ключи шифрования.
4. После запуска войдите заново. Пароль владельца сохраняется. Если в старом
   `app_users` было несколько пользователей, владелец определяется по
   `ADMIN_USERNAME`; при неоднозначности миграция останавливается.
   Остальные старые аккаунты получают только просмотр Основного — перепроверьте права.
5. Откройте **Пользователи и доступ**. Для отдельной базы сначала создайте
   пространство, затем пользователя с доступом к нему. Для работы в общей базе
   создайте пользователя и выберите **Основное**.
6. Проверьте вход нового пользователя, запрещённые действия, новые и старые
   подписки. После переключения базы обновите ранее открытые формы.

При первом включении служебной базы автоматически создаётся согласованный
SQLite-снимок основной базы в `data/migration-backups/`. Если снимок создать
нельзя, например закончилось место, перенос учётных записей не активируется.
Этот снимок НЕ заменяет полный backup конфигурации и ключей.

## Важные ограничения и эксплуатация

- Максимум 8 запущенных пространств, включая Основное. Каждый процесс расходует
  дополнительную RAM и создаёт свои фоновые запросы. Квот CPU/RAM по сотрудникам
  и нагрузочного теста на вашем VPS пока нет.
- Это логическое разделение внутри одной установки, **не песочница для взаимно
  недоверенных владельцев**: процессы имеют одного системного пользователя.
  Для жёсткой изоляции нужны отдельные контейнеры/VPS и сетевые ограничения.
- Одна удалённая 3x-ui/Remnawave закрепляется за одним пространством, иначе их
  массовые операции могут конфликтовать. Проверяется адрес панели; известный
  внутренний `local-3xui` и настроенный публичный IP:2053 учитываются как одна панель.
  Неизвестные DNS-алиасы автоматически определить надёжно нельзя. Не добавляйте
  одну физическую панель под разными адресами в независимые базы.
- Локальная управляемая 3x-ui остаётся за Основным. Новое пространство не
  устанавливает отдельную 3x-ui автоматически. Для сотрудников, которым нужны
  существующие узлы, используйте общую базу с ограниченными правами.
- Перенос узла между пространствами и удаление пространства не реализованы;
  записи принадлежности узлов специально не освобождаются автоматически.
- Для полного backup после обновления используйте `agg` → 5 при стандартном
  расположении `data` внутри каталога установки: архив включает `control.db`,
  все базы и ключи из `.env`. Старый JSON web-backup не является копией всех
  пространств и пользователей. Если DATA_DIR вынесен наружу, резервируйте его отдельно.
- Откат требует согласованного старого кода, баз и ключей. Не подменяйте один
  `app.js` и не удаляйте `control.db`. Записи после снимка при полном откате
  потеряются; изменения на удалённых панелях локальный backup не отменяет.

## Что проверено

На Node.js 22.14.0 с реальными SQLite и дочерними процессами:

- 8 новых тестов: миграция, права, отзыв сессий, разные базы с одинаковыми ID,
  публичные ссылки, отсутствие доступа в чужую базу, старые формы, профиль
  настроек, реестр удалённых панелей и сохранение состояния после перезапуска.
- Компиляция 19 EJS-шаблонов; синтаксис изменённых JS и установщика.
- 56 тестов установщика дополнительных панелей — успешно.
- Общий JS-набор: 159 тестов, 150 успешно, 5 ошибок, 4 пропуска.
  Те же 5 ошибок воспроизведены отдельно на коде ДО этого изменения:
  `node-inbound-sync` (текст ошибки отсутствующего inbound), два устаревших
  ожидания `spectrum-clear`, `subscription-device-registry` (служебный доступ),
  `subscription-portal-traffic` (fallback автовыбора).

Полностью зелёного общего набора пока нет. Проверка Docker/Linux на реальном
VPS, нагрузочная проверка, визуальная мобильная проверка и восстановление
полного серверного архива ещё нужны до рабочего развёртывания.
