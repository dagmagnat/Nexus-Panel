# AmneziaWG 3.1 из 3x-ui в общей подписке Nexus / INCY

Реализация: 2.7.24, 2 ноября 2026. Основа — предоставленный архив `Nexus-Panel-main (5).zip`, версия 2.7.22. Разработка выполнена в отдельной папке; старая локальная 2.5.1 не заменялась.

## Использование

1. В актуальной 3x-ui создайте inbound **AmneziaWG**, сгенерируйте параметры **3.1** штатной кнопкой панели и сохраните. Запомните ID. UDP-порт должен быть доступен извне; для Docker опубликуйте именно UDP.
2. Nexus → **Узлы → Добавить → Тип: 3x-ui**. Укажите URL панели, её путь, API Token или логин/пароль. В поле **Протокол подписки** выберите **AmneziaWG 3.1 · INCY**, затем введите Inbound ID. Несоответствие протокола отменяет добавление до записи узла.
3. Выберите страну/название. Чтобы назначить сервер всем существующим клиентам, отметьте **Добавить клиентов из агрегатора**. Это существующая операция создания отсутствующих клиентов; повторный запуск не должен создавать дубли.
4. Для назначения отдельному клиенту откройте редактор пользователя, отметьте узел и сохраните. Можно одновременно отметить VLESS, Remnawave и AWG.
5. Откройте страницу подписки и нажмите **INCY → Добавить**. В актуальном INCY на iOS/Android AWG появится отдельной локацией рядом с другими серверами.
6. Если подписка уже добавлена в INCY через SUB или JSON Nexus, обновите её. Старые UUID, slug и ссылки не меняются.

Nexus подключает существующий AWG inbound в 3x-ui. Серверную установку и генерацию параметров выполняет сама 3x-ui. Отдельный раздел Nexus «VPN-сервисы» не требуется для этого сценария.

## Адрес сервера

Поддерживаются стандартные Share address стратегии 3x-ui: адрес узла, конкретный Listen или Custom. Можно использовать публичные endpoints из `streamSettings.externalProxy`. Для локальной `local-3xui` нужен заданный публичный VPN-адрес либо Custom в inbound. Нельзя выдавать клиентам внутреннее Docker-имя API.

Если API доступно по одному домену, а VPN работает на другом IP/домене, задайте **Share address: Custom** в 3x-ui. Порт API и UDP-порт AWG — разные параметры.

## Форматы подписок

| Адрес | Результат |
| --- | --- |
| `/sub/<slug>`, `/sub-plain/<slug>` | Общий список ссылок, включая `amneziawg://<base64url-conf>#<имя>` и VLESS |
| `/json/<slug>?format=incy` | Массив Xray-конфигураций и AWG-контейнеров INCY |
| `/<slug>?format=incy` | То же для чистой ссылки, если slug допускает её использование |
| `/json/<slug>` с User-Agent INCY | Смешанный JSON автоматически |
| Обычный `/json/<slug>` для Xray/Happ | Прежние Xray-конфигурации без AWG-контейнеров |

Кнопка INCY использует смешанный JSON, если JSON-ссылки включены, иначе общий SUB. В JSON сохраняются настройки маршрутизации и автоподключений VLESS; AWG выдаётся самостоятельным сервером и не включается в Xray-балансировщик.

По официальной документации INCY AmneziaWG и AWG-контейнеры поддерживают **iOS/Android**. Desktop INCY пока их не поддерживает. Обновите приложение до версии с поддержкой AWG 3.1. Клиенты без AWG-движка не смогут подключиться к этому серверу.

## Как устроена интеграция

Основные контуры проекта: Express/EJS и SQLite в `app.js`; узлы `nodes`; идентичность подписчика `clients.uuid/sub_slug`; назначения и лимиты `client_nodes`; снимки inbound в `node_inbound_cache`. Remnawave имеет свой адаптер, а 3x-ui использует актуальный Clients API с совместимостью со старым API. Отдельные VPN-сервисы реализованы в `lib_vpn_manager.js`; агент `node-agent/` пока является самостоятельным контуром управления.

AWG подключён к обычным `nodes/client_nodes`, поэтому участвует в существующем назначении клиентам, массовом создании, отключении, продлении, учёте срока/лимита и удалении из узла. Дополнительной миграции схемы БД нет.

- Для AWG используется `/panel/api/clients/add`, `update`, `attach` и `detach`. Legacy `inbounds/addClient` для создания AWG не используется. Работает также авторизация логином/паролем, если сама 3x-ui предоставляет Clients API.
- Ключи и адреса выдаёт 3x-ui. После создания/обновления Nexus перечитывает inbound, чтобы новый клиент сразу попал в подписку.
- Конфигурация клиента берётся только из его записи в **выбранном inbound**. Общая запись Clients может описывать другой туннель и не является источником ключей AWG.
- При редактировании срока/лимитов не пересылаются чужие ключи, адреса и keepalive из глобальной записи. Это относится также к VLESS-редактированию общей записи. Существующий flow общей записи сохраняется при изменении AWG.
- Сохраняются DNS, IPv4/IPv6, preshared key, MTU, Jc/Jmin/Jmax, S1–S4, H1–H4, I1–I5 и весь набор 3.x: HeaderProtectionKey, ContentPaddingAddition, RekeyAfterTime, RekeyTimeout, RejectAfterTime, KeepaliveTimeout, MaxHandshakeAttempts, RandomTrailers, DisableCookies. Диапазоны, включая PersistentKeepalive, не преобразуются в числа.
- MTU соответствует алгоритму 3x-ui: явный `server.mtu` либо `max(1420 - S4, 1280)`.
- Серверный private key не включается в клиентский конфиг. Если нет ключа или адреса нужного клиента, Nexus не подставляет первого клиента inbound. Управляющие символы в строковых значениях запрещены.

Файлы реализации: `lib_amneziawg.js`, `app.js`, `lib_subscription_links.js`, `lib_local_inbound_port.js`, `views/nodes.ejs`, `views/open_sub.ejs`.

## Обновление установленной панели из пакета

Полный ZIP содержит исходники проекта. Не заменяйте свою `data/` и `.env`. Для существующей установки достаточно файлов из `Nexus-Panel-2.7.24-AmneziaWG-patch.zip`; полный архив подходит для отдельной установки/сборки.

Пример для стандартной Docker-установки (путь своей панели проверьте через `pwd`):

```bash
cd /opt/3xui-aggregator
docker compose stop
backup="/root/nexus-before-awg-$(date +%Y%m%d-%H%M%S).tar.gz"
tar --exclude='./node_modules' --exclude='./.git' -czf "$backup" .
# Загрузите patch.zip на сервер и распакуйте его ПОВЕРХ этой папки:
unzip -o /root/Nexus-Panel-2.7.24-AmneziaWG-patch.zip -d .
docker compose up -d --build
docker compose logs --tail=80
```

Патч не содержит БД, `.env`, `node_modules` или учётных данных. Переданные в архиве настройки реального сервера не использовались. Для отката остановите контейнеры, восстановите архив `$backup` в прежнюю папку и пересоберите контейнеры. Новые подключения AWG после отката старой версии не будут выдаваться до возврата версии с поддержкой AWG.

## Проверки и границы проверки

На Windows / Node.js 22.23.2 выполнены:

- Проверка синтаксиса JavaScript и компиляция 20 шаблонов EJS.
- Unit-проверки параметров AWG 3.1, ключей конкретного клиента, IPv6, диапазонов, MTU, запрета подстановки чужой конфигурации и UDP-публикации Docker.
- Сквозной HTTP-тест с настоящими Express/SQLite и имитацией актуального API 3x-ui: добавление узла всем существующим клиентам, разные ключи, SUB и смешанный JSON, User-Agent INCY, чистые ссылки, перезапуск, срок, продление, лимиты, отключение и отсоединение.
- Полная база проверок сравнена с неизменённым архивом: исходно 257 тестов, 227 пройдено, 12 ошибок, 18 пропущено; после добавления — 261 тест, 231 пройден, те же 12 ошибок и 18 пропусков. Новые четыре теста проходят.

В исходном архиве уже не проходят проверки client-transfer (3), Docker bootstrap/compose (2), apiGet VM-стенда, сообщения отсутствующего inbound, Spectrum CSS, старого HWID/служебного доступа (2), списка автоподключений и workspace/RBAC. Они не исправлялись в рамках AWG. `npm run check` на этой Windows-среде также упирается в исходную Unix-команду `>/dev/null`; JS/EJS и Python CLI проверены напрямую.

Живой сервер 3x-ui и мобильное приложение INCY в этой сессии не предоставлены. Реальное VPN-рукопожатие, firewall и прохождение трафика на вашем сервере нужно проверить после установки: обновить подписку, выбрать AWG, подключиться, открыть сайт и проверить трафик в 3x-ui. HTTP-тест подтверждает интеграцию и форматы, а не сетевую доступность сервера.

## Уточнение маршрутизации и устройств, 2.7.24

Правила раздела Nexus «Маршрутизация JSON» исполняются Xray. В нативном AmneziaWG-конфиге нет интерпретатора Domain/GeoSite/GeoIP и правил Xray DNS. Сам факт импорта AWG в одну подписку не переносит эти правила. AWG-узлы больше не доступны для назначения в этой форме; сохранение формы отфильтрует прежние ложные назначения AWG, сохранив выбранные Xray-узлы и списки правил.

По состоянию на 2 ноября 2026 в [трекере INCY](https://feedback.incy.cc/issues/cmu0g146f00bnj785k90v631x) маршрутизация AmneziaWG для iOS отмечена как Planned. [Другой запрос по AWG 3.1](https://feedback.incy.cc/issues/cmua2wm2t007rz34dvmxn8xn9) открыт; там есть отзыв пользователя об успешно применённом профиле, но нет подтверждения разработчиков и гарантии для конкретной версии. Передача routing/autorouting-профиля сама по себе не доказывает его применение AWG-движком. В этом пакете не заявляется перенос полной маршрутизации на AWG.

Возможное частичное решение — маршруты IP/CIDR через AllowedIPs, если приложение их корректно применяет. Оно не эквивалентно правилам доменов/GeoSite с DNS, обновлениями адресов CDN и приоритетами. Маршрутизация на VPS также не эквивалентна обходу VPN с домашнего/мобильного подключения: пакет уже достиг сервера.

В этой версии исправлен серверный порядок: AWG-контейнеры выдаются между Xray-конфигурациями согласно sort_order узлов. Автовыбор остаётся перед физическими узлами и использует VLESS/Xray. Приложение может дополнительно сортировать серверы локально.

Лимит устройств Nexus пока регулирует реестр запросов подписки. Один клиент Nexus получает один AWG-peer; увеличение device_limit до 20 не создаёт 20 ключей. Для одновременной независимой работы устройств нужна отдельная пара ключей и адрес для каждого. Перспективная схема — ленивое создание peer при первом разрешённом запросе с HWID и выдача только привязанного к этому HWID конфига. Нужны также отзыв peer при удалении устройства, согласованное продление/отключение, суммарный трафик и защита от одновременного выделения одного слота. Это отдельная доработка, не реализованная в 2.7.24.
