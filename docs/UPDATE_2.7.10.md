# Nexus 2.7.10 — оптимизация входа и повседневной работы

Патч подготовлен 12 октября 2026 года. На боевом сервере не установлен, GitHub не обновлялся.

## Что исправлено

- Страница после входа больше не рассчитывает историю всех клиентов и нод, не опрашивает удалённые панели даже при `?online=1`, не записывает и не чистит снимки при каждом открытии. Трафик, топ потребления и окно лимитов загружаются отдельными защищёнными запросами. Тяжёлые скрытые разделы загружаются при открытии.
- Проверка пароля асинхронная, с повторной проверкой пользователя и блокировки попыток после ожидания. Исправлена прежняя ошибка CSRF при выходе из сессии. Пароли, алгоритм хэширования, права, защита сессий и CSRF не ослаблены.
- Длинные клиентские отчёты уступают цикл событий между небольшими группами клиентов. Другие страницы могут отвечать, пока строится отчёт.
- Онлайн-запросы нескольких вкладок используют общий серверный снимок на 5 секунд и один текущий опрос. Браузер и CDN эти ответы не кэшируют. Кэш не используется для авторизации, выдачи доступа или решений по квотам.
- Git-метаданные в настройках читаются асинхронно, два запроса параллельно, результат кэшируется на минуту. Нет запуска блокирующего git на каждом переходе.
- Обычный опрос Remnawave запрашивает последние три календарных дня. Первый сбор, изменение источника, полная суточная сверка и явный сброс используют прежнее окно до 370 дней. После остановки сборщика учитывается пропущенный период. Дневная история и отдельные отметки сброса сохраняются; поздние изменения старых дней обнаруживаются полной сверкой. Неудачный запрос не обновляет её контрольную отметку и не обнуляет известный расход.
- Каталог пользователей одной Remnawave-панели с одинаковыми учётными данными читается один раз за сбор. Старые дневные записи API-кэша удаляются после истечения TTL, а не накапливаются бессрочно.
- Локальные записи 3x-ui сгруппированы в транзакции по 25 связей; общий снимок и счётчики Remnawave записываются транзакционно. Транзакции не держатся во время ожидания сети. Чистка старых снимков выполняется в фоне раз в час, по прежним срокам хранения: 370 дней общие/нодовые, 30 дней клиентские. Нода-зависимый дневной ledger этим не очищается.
- Лимиты на главной отображаются по 20 строк с поиском по всем загруженным данным, выбором 20/50/100/200/Все и страницами. Фоновое применение квот продолжает работать без открытого браузера.
- HTML получает `Server-Timing: nexus;dur=...`. Запросы управления дольше секунды записывают в журнал `nexus_slow_request` с маршрутом, статусом и длительностью, без query string, паролей, токенов и содержимого форм. Порог можно изменить переменной `NEXUS_SLOW_REQUEST_MS` (мс, минимум 100).

Пагинация пользователей, политика HWID, независимые квоты и их исправления из 2.7.8/2.7.9 включены. Подробности — в соответствующих инструкциях. Пользователи и настройки не удаляются; Remnawave/XUI и ноды обновлять для установки этого патча не требуется.

## Проверенный локальный результат

Сравнение с неизменёнными файлами ранее переданного патча 2.7.9, одинаковая синтетическая SQLite-база: 1000 клиентов, одна нода, 120 000 клиентских снимков. Запрос `/dashboard?online=1`, три последовательных открытия после входа:

| Показатель | 2.7.9 | Оптимизированная версия |
|---|---|---|
| Главная, локальные HTTP-замеры | 955 / 899 / 914 мс | обычно 18–33 мс |
| HTML главной, до сжатия | 947 696 байт | 226 367 байт |
| Настройки во время построения топ-отчёта | не измерялись | около 64–75 мс |

Это не замеры VPS пользователя и не обещание такой же скорости. Сетевая задержка, DNS/TLS, reverse proxy, CPU, диски, RAM/swap и объём реальной базы влияют отдельно. Само вычисление большого отчёта остаётся работой сервера; оно не замедляет открытие главной и разбито на небольшие порции. Отчёты показывают время сохранённого снимка; для свежего сбора есть явная кнопка.

## Установка

Накопительный патч для существующей Nexus **2.7.7 / 2.7.8 / 2.7.9**. Применять только на сервере Nexus. Публичная команда обновления и `panel-script-v1.sh --update` этот локальный архив не устанавливают.

Сначала резервная копия всего приложения и всех баз, особенно внешних DATA_DIR/control/workspaces/volumes. Рекомендуется проверить копию данных. Первый запуск может быть дольше обычного из-за построения индекса существующей истории.

Для стандартного Docker-развёртывания загрузите архив на сервер:

```bash
unzip Nexus-Panel-2.7.10-performance-patch.zip -d /root/nexus-performance-2.7.10
cd /root/nexus-performance-2.7.10
bash apply-node-traffic-update.sh /opt/3xui-aggregator
```

Вместо `/opt/3xui-aggregator` укажите действительный каталог установленной Nexus. Helper проверяет приложение, требует YES, останавливает только `aggregator`, сохраняет весь каталог с `.env` и локальными базами рядом в архив, накладывает PATCH_FILES.txt и пересобирает только этот сервис. Внешние данные он не копирует автоматически.

Для systemd: остановить только Nexus, сохранить весь каталог приложения и внешние базы/пространства, скопировать файлы из PATCH_FILES.txt с сохранением путей, выполнить `npm ci --omit=dev` и запустить свой сервис. Имя сервиса не угадывается.

Откат: остановить Nexus, восстановить исходники и базы из полной резервной копии, пересобрать и запустить. Не подменять базу работающего процесса. Удалённые изменения пользователей/сквадов откат Nexus сам не отменяет.

## Проверка после установки

1. Версия интерфейса должна стать 2.7.10. Проверить вход, выход, главную, пользователей и настройки.
2. Открыть «Скачано», «Кто больше потратил» и «Лимиты»: сведения должны загрузиться без повторного входа. Проверить страницы лимитов и поиск.
3. На странице трафика выполнить явный сбор и проверить несколько отдельных нод/клиентов. Старые суммы и независимые сбросы должны сохраниться.
4. В DevTools → Network смотреть ответ Document и его Server-Timing. Короткое `nexus;dur`, но длинное ожидание соединения указывает на необходимость отдельно проверить сеть/proxy. Длинное `nexus;dur` — на работу сервера приложения.
5. Для стандартного Compose в каталоге Nexus: `docker compose logs --tail=200 aggregator`. Сообщения `nexus_slow_request` помогают найти оставшиеся задержки, но не доказывают их конкретную причину.

## Локальные проверки

- `npm run test:performance`: кэш/single-flight, уступание цикла событий, сохранение истории и сброса, полная/короткая сверка Remnawave, настоящие HTTP-запросы к большой базе и конкурентный опрос онлайн.
- Целевые проверки пользователей, квот, HWID, прав и входа; настоящая фикстурная Remnawave 3.3.0 проверяет единственный запрос каталога для двух нод.
- Edge 1440/390: открытие отложенных отчётов, пагинация лимитов, поиск, отсутствие JS-ошибок и горизонтального переполнения. Браузерная проверка включается `NEXUS_BROWSER_QA=1` в подготовленной локальной среде.
- JS syntax и все 20 EJS-шаблонов; Bash syntax helper. Полный исторический набор не зелёный: 215 тестов, 189 pass, 10 известных падений, 16 пропусков. Категории старых падений перечислены в PROJECT_HANDOFF.md; в этой доработке они не переделывались.

## Что не изменялось

Расположение каталогов не является установленной причиной тормозов. SQLite не заменялась на PostgreSQL; режим журналирования и гарантии записи не ослаблялись. Доступ к боевому серверу не выполнялся, инфраструктурная причина его задержек не подтверждена. После установки нужны замеры именно его ответов; при оставшихся задержках понадобятся характеристики VPS и журналы медленных запросов.
