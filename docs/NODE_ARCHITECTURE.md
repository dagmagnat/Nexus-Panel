# План архитектуры Nexus Panel / Nexus Node

Статус: проект следующего этапа. Spectrum Clear не включает сетевой агент и не меняет текущий способ подключения узлов.

## Цель

Один установочный сценарий должен предлагать три роли:

1. **Panel** — центральное управление без локальной ноды;
2. **Node** — лёгкий агент на сервере выхода;
3. **Panel + Node** — обе роли на одном сервере.

Панель в одной стране сможет управлять нодой в другой стране, не требуя открывать наружу админку 3x-ui или SSH.

## Компоненты

| Компонент | Ответственность |
|---|---|
| Nexus Panel | клиенты, подписки, лимиты, маршрутизация, UI, аудит, задания |
| Nexus Node Agent | конфигурация Xray/VPN, локальная статистика, health, выполнение подписанных заданий |
| Enrollment service | одноразовое безопасное присоединение ноды |
| Control channel | команды и статусы между панелью и нодой |
| Data plane | клиентский VPN-трафик непосредственно через ноду |

Обычный клиентский трафик не должен проходить через сервер панели. Панель управляет конфигурацией, а нода является точкой входа/выхода трафика.

## Безопасное подключение ноды

Не следует хранить постоянный API-ключ, показанный в открытом виде навсегда. Рекомендуемый процесс:

1. При установке Node создаётся одноразовый enrollment token с коротким сроком жизни.
2. Администратор вводит token в Panel.
3. Panel и Node обмениваются постоянными идентификаторами и ключами.
4. Дальнейшее соединение использует mTLS или подписанные запросы с ротацией ключей.
5. Token немедленно отзывается после первого успешного присоединения.
6. В панели показываются fingerprint, время подключения и возможность отозвать ноду.

Обязательны защита от повторного воспроизведения, ограничение времени, журнал действий и явное подтверждение опасных операций.

## Соединение

Предпочтительный вариант — исходящее постоянное соединение Node → Panel по HTTPS/WebSocket. Это упрощает работу за NAT и firewall: на ноде не требуется открывать отдельный административный порт.

Через канал передаются:

- heartbeat и версия агента;
- доступные возможности;
- описание transport/inbound;
- агрегированная статистика;
- задания создания, обновления и отключения клиентов;
- результат задания с идемпотентным `operation_id`.

Секреты клиентов передаются только когда это необходимо для конфигурации конкретной ноды и не попадают в обычные логи.

## Совместимость с текущими клиентами

- Центральная таблица `clients` остаётся источником UUID и `sub_slug`.
- При присоединении новой ноды существующие клиенты назначаются явно или пакетной задачей.
- Добавление Node Agent не изменяет уже выданные URL подписок.
- Текущие подключения 3x-ui/Remnawave остаются доступными в переходный период через адаптеры.

## Этапы реализации

### Этап A — фундамент

- формальная схема capabilities;
- таблицы nodes/credentials/operations без замены текущих `clients`;
- одноразовое присоединение;
- heartbeat, версия, health и отзыв ноды.

### Этап B — управление Xray

- чтение существующего inbound;
- идемпотентное создание/обновление клиента;
- локальный сбор трафика;
- очередь операций и безопасный повтор.

### Этап C — миграция

- мастер переноса текущего 3x-ui узла в Nexus Node;
- dry-run и сравнение клиентов;
- переключение только после совпадения UUID/лимитов;
- автоматический откат конфигурации ноды.

### Этап D — VPN-сервисы

- WireGuard/AmneziaWG/Outline через capability-модули;
- единые статусы и резервные копии;
- обновление агента отдельно от панели.

## Что нужно решить перед кодом

- разрешённые версии Linux и Docker;
- нужен ли режим без Docker;
- допустима ли только исходящая связь Node → Panel;
- модель владения несколькими панелями/нодами;
- сроки хранения статистики;
- процедура восстановления ключей после потери панели;
- стратегия автоматического обновления агента.

До утверждения этих решений Node Agent не должен внедряться в рабочее обновление дизайна.
