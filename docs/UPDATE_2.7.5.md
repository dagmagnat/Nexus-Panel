# Nexus Panel 2.7.5 — несколько панелей на одном VPS

Локальная сборка, 9 сентября 2026. В GitHub не опубликована; на рабочий VPS
пользователя не устанавливалась. Все изменения 2.7.4 сохранены.

## Что добавлено

В конце мастера новой установки Nexus появляется выбор:

- 0 — только Nexus / ничего не добавлять, по умолчанию;
- 1 — дополнительно установить 3x-ui;
- 2 — дополнительно установить Remnawave Panel;
- 3 — установить обе дополнительные панели;
- r — повторить незавершённый запуск сохранённого плана.

На существующей панели: `agg local-panels` или пункт **9** меню `agg`.
Это не перенос и не обновление чужих установок: мастер создаёт собственные
изолированные контейнеры. Внешние панели по-прежнему подключаются как раньше.

Для каждой новой дополнительной панели отдельно выбирается версия:

1. Последняя стабильная на момент запуска.
2. Одна из пяти последних стабильных версий, полученных из GitHub API.
3. Ручной номер официального релиза, с проверкой существования.

Dev, beta и draft не выбираются. При недоступном каталоге можно ввести номер,
но без подтверждения GitHub установка не продолжится. Несуществующий Docker-
тег не заменяется молча на `latest`. Выбранный тег сохраняется: обновление
Nexus не обновляет и не понижает версии дополнительных панелей.

На момент проверки каталог вернул:

- 3x-ui: v3.7.0, v3.6.0, v3.5.0, v3.4.2, v3.4.1;
- Remnawave: 3.4.3, 3.4.2, 3.4.1, 3.4.0, 3.3.2.

Это справочная информация, не фиксированный список внутри установщика.
[Релизы 3x-ui](https://github.com/MHSanaei/3x-ui/releases),
[релизы Remnawave](https://github.com/remnawave/backend/releases).

## Адреса и порты

Например, все три DNS-записи указывают на IP одного VPS:

| Компонент | Адрес |
|---|---|
| Nexus | `https://panel.example.com` |
| 3x-ui | `https://xui.example.com/случайный-путь/` |
| Remnawave | `https://rw.example.com` |

Для 3x-ui можно выбрать IP: `https://IP:2053/случайный-путь/`. В этом режиме
используется локальный сертификат Caddy, браузер выдаст предупреждение.
Для доверенного браузером HTTPS используйте домен. IP поддерживается также
для самой Nexus существующим мастером.

Remnawave в этом мастере работает только через отдельный домен и HTTPS, не
через IP и не в подпапке Nexus. Backend, PostgreSQL, Redis и метрики не
публикуются на интерфейсах хоста. Это соответствует требованию использовать
[reverse proxy](https://docs.rw/install/remnawave-panel/) и
[отдельный домен для Caddy](https://docs.rw/install/reverse-proxies/caddy/).

Входящий HTTPS обслуживает один Caddy Nexus. Если Nexus работала только по IP
без Caddy, мастер добавит его. Если Caddy уже есть, добавит сайты в него,
а не будет поднимать второй контейнер на 80/443. Разные домены обязательны.

Порты Xray задаются при установке 3x-ui, по умолчанию `8443/tcp,8443/udp`.
Их нужно использовать при создании inbound. Мастер публикует выбранные порты,
но не создаёт inbound и маршрутизацию за администратора. Поддерживается до
32 отдельных портов, диапазоны не поддерживаются. 80/443 зарезервированы для
HTTPS панелей; один IP:443 одновременно занять Caddy и Xray не могут.

Проверяются пересечения с портом Nexus, панелью 3x-ui, TCP/UDP слушателями
сервера. Чужие службы не останавливаются, правила firewall не открываются
автоматически. Разрешите нужные порты в firewall VPS и у провайдера сами.
Nexus сохраняет свои существующие системные helper-сервисы без изменения.

## Устройство установки и безопасность

- Дополнительные панели — отдельный Compose-проект `nexus-local-<экземпляр>`.
  Обновление/остановка контейнера Nexus не перезапускает их контейнеры и VPN.
  Во время перезапуска общего Caddy вход в их веб-панели кратко недоступен.
- Данные находятся в `/opt/nexus-local-panels/<экземпляр>/`, а не внутри
  рабочей папки Nexus. Отдельные базы и случайные секреты у каждой панели.
- `state.json` хранит выбранные версии, адреса и параметры запуска.
- `3xui/credentials.json` — сгенерированные логин, пароль и случайный путь.
  Каталог доступен root, файл имеет права 0600. Пароль не печатается в журнал.
- До публичного запуска 3x-ui её база инициализируется контейнером без сети,
  затем CLI проверяет отсутствие стандартной учётки и правильность порта/пути.
- 3x-ui использует bridge-сеть, без `privileged` и без host network. Fail2ban
  получает NET_ADMIN/NET_RAW внутри контейнера, как в официальном Docker-
  варианте. Работоспособность IP-ограничений проверьте на тестовых клиентах.
- Remnawave использует свою приватную сеть для БД/Redis. Front-сеть общая
  только с Nexus/Caddy; базы к ней не подключены.
- Сертификаты и Docker-данные не объединяются с клиентской базой Nexus.
- Управляемый Compose override восстанавливается при обновлении Nexus.
  Найденный пользовательский override мастер не перезаписывает; требуется
  ручное объединение конфигурации. Обычный старый механизм обновления Nexus
  заменяет программные файлы, поэтому резервная копия всё равно обязательна.
- Повторная установка уже управляемого компонента не сбрасывает пароли и
  не меняет версии. Пункт `r` продолжает запуск с сохранённым состоянием.

Для Remnawave параметры окружения и версии БД/Valkey берутся из файлов
именно выбранного официального релиза, а не из движущейся ветки `main`.
Неизвестная схема или несовместимая старая версия отклоняется до запуска.
Ручной номер не означает поддержку любого исторического релиза: старые
версии с другой схемой БД/секретов требуют своего официального установщика.

## Что сделать после установки

### 3x-ui

1. Прочитайте root-файл `3xui/credentials.json`, войдите по напечатанной ссылке.
2. Создайте inbound на опубликованном порту, например 8443, настройте протокол
   и маршрутизацию. Сертификат веб-панели сам по себе не настраивает TLS inbound.
3. Создайте API-токен в 3x-ui.
4. В Nexus добавьте узел: адрес `http://local-3xui:2053`, отдельное поле Panel
   Path — случайный путь из файла, API-токен и ID inbound. Этот внутренний
   HTTP-адрес доступен из контейнера Nexus, не из браузера на компьютере.
   Вместо него можно использовать публичный домен HTTPS.

### Remnawave

1. Сразу после запуска откройте HTTPS-домен и создайте администратора.
2. Подключите Remnawave Node по официальной инструкции — на этом же VPS
   или другом. **Мастер устанавливает Panel, не Node**: сама панель не
   обрабатывает VPN-трафик. Это отдельный компонент, не агент Nexus Node.
3. Настройте профиль, Internal Squad, Host и API-токен.
4. Добавьте Remnawave в Nexus по публичному HTTPS-домену и API-токену.

Автоматического создания API-токенов, inbound, клиентов, оплат и маршрутов
внешних панелей нет. Мастер печатает адреса и дальнейшие действия.

Для отдельной служебной панели истёкших подписок из 2.7.4 другой VPS не нужен:
важна независимая удалённая панель и база, а не отдельное железо. Не используйте
один и тот же экземпляр 3x-ui/Remnawave одновременно как обычный и служебный
узел без предусмотренной в 2.7.4 изоляции.

## Эксплуатация, ресурсы и резервные копии

Пример для стандартного экземпляра:

```bash
cd /opt/nexus-local-panels/default
docker compose ps
docker compose logs --tail=100 local-3xui
docker compose logs --tail=100 local-remnawave
```

Состав контейнеров зависит от выбранных компонентов. Не делитесь секретами
из `.env`, credentials.json, API-токенами или ссылками подписок.

Не понижайте версию после миграции БД простой заменой тега. Этот мастер не
выполняет автоматические обновления/откаты сторонних панелей; для них нужны
backup, совместимость схемы и инструкции соответствующего проекта.

Обычный backup Nexus **не включает** `/opt/nexus-local-panels/`. Сохраняйте
этот каталог и согласованные копии баз отдельно: PostgreSQL через `pg_dump`
или при остановленной БД; SQLite через backup либо при остановленной 3x-ui.
Не копируйте живой PostgreSQL как обычную папку без согласованного снимка.

Удаление Nexus не удаляет дополнительные базы и контейнеры. VPN может
продолжать работать, а веб-доступ через удалённый Caddy пропадёт. Их отдельное
удаление намеренно не автоматизировано.

Remnawave рекомендует минимум 2 CPU, 2 ГБ RAM и 20 ГБ диска; рекомендуемая RAM
— 4 ГБ. Для совместного размещения нужен запас под Nexus, Xray, клиентов и
логи. Мастер показывает CPU и свободный диск, но не гарантирует производительность.
[Требования Remnawave](https://docs.rw/install/requirements/).

## Проверки и ограничения

- 22 новых unit/dry-run теста мастера прошли: версии, ввод, конфликты,
  идемпотентность, приватные сети, защита override, порядок инициализации.
- Реальный Docker Compose 5.5.1 принял конфигурацию провайдеров и объединение
  Nexus/Caddy как при существующем Caddy, так и без него (`config`, без запуска).
- Проверен Bash-синтаксис install.sh через Git Bash.
- GitHub API вернул актуальные списки релизов обоих проектов; исходные файлы
  выбранных релизов доступны. TLS-проверка сертификатов не отключалась.
- Регрессионный набор Nexus: 60 прошли, 4 Linux/Bash-проверки пропущены в
  штатном Windows-окружении. Пробный запуск через Git Bash дал 2 ошибки
  окружения старого тестового стенда (`/var/log` и запуск `/usr/bin/env`),
  поэтому полноценной проверкой Linux-установки это не считается.

Контейнеры, Linux/VPS, сертификаты ACME, реальный вход и VPN-трафик здесь
не запускались: локально нет Docker Engine. Перед рабочей эксплуатацией
нужна проверка на тестовом VPS и тестовом клиенте. Это подготовленная локальная
сборка, а не подтверждение успешной установки на вашем сервере.
