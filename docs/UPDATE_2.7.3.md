# Nexus Panel 2.7.3 — отчёт по изменениям

Локальная сборка на базе ранее подготовленного проекта 2.7.2, а не новая
проверка текущей ветки GitHub. На сервер пользователя не устанавливалась.

## Интерфейс

- Шрифт кнопок верхней панели клиентов, значений фильтров и основных данных
  таблицы на компьютере увеличен до 12 px; подписи фильтров — 11 px.
- Трафик показан компактно в две строки. Красным отмечен исчерпанный лимит;
  наведение показывает разбивку, нажатие открывает существующее окно лимитов
  узлов, если для клиента оно есть. Данные окна тоже обновляются.
- Дата окончания доступа теперь подписана «Срок истёк» в desktop-статусе,
  чтобы не путать её с исчерпанием ГБ.

## Расход и лимиты

Причина устаревших цифр: автообновление клиентов запрашивало только онлайн,
а расход рисовался при загрузке страницы из локальных данных. Более того,
рендер страницы мог записать в БД старые счётчики из кеша inbound.

Добавлен `/clients/usage.json` для авторизованного администратора. Он
немедленно отдаёт последний снимок и запускает общий фоновый сбор, если
после предыдущего завершения прошло 30 секунд. Одновременные запросы
разделяют один сбор. Узлы опрашиваются с параллелизмом 4. Пока сбор идёт,
интерфейс забирает снимок раз в 3 секунды; период новых сборов не равен
интервалу онлайн-проверки 10 секунд. Ошибки обозначаются явно, старые значения
сохраняются. Валидный нулевой счётчик после сброса заменяет прежний расход.

Для 3x-ui используются массовые счётчики API/inbound без сотен последовательных
поштучных запросов. Если конкретная старая версия отдаёт статистику только
по одному клиенту, потребуется отдельный адаптер; отсутствие данных теперь
отмечается, а не превращается в ноль. H1Cloud этим обновлением не получил
нового сборщика трафика.

В клиентах добавлены:

- «Трафик: больше потрачено» / «Трафик: меньше потрачено»;
- «Показать: с лимитом ГБ»;
- «Показать: лимит ГБ исчерпан».

Фильтр считает исчерпанным общий лимит либо хотя бы один лимит назначенного
узла, включая отключённую привязку. Ноль ГБ означает безлимит. Если выбран
узел, узловые лимиты и сортировка расхода относятся к нему; общий лимит
остаётся общим, даже при фильтрации. Эти изменения отображают состояние,
не меняют правила блокировки доступа и не сбрасывают счётчики.

Дашборд → «Кто больше потратил»: под отчётом за период добавлен блок
«Лимиты трафика клиентов», с фильтром узла, поиском и сортировками. Его
текущие счётчики намеренно отделены от дневного/недельного расхода.

Важное ограничение Remnawave: `userTraffic.usedTrafficBytes` — счётчик
пользователя удалённой панели, не измерение отдельно взятого физического
сервера. Если несколько узлов Nexus ссылаются на одного пользователя одной
Remnawave-панели, этот счётчик может повторяться в привязках и суммироваться
повторно. Отдельная нормализация таких общих счётчиков в этот выпуск не входит.

## Онлайн и сортировки

Раньше фильтр по узлу проверял только назначение узла, а онлайн — любой узел
клиента. Теперь учитывается список узлов, на которых он обнаружен. Поиск
удалённого логина на сервере ограничен привязками проверяемого узла; совпадение
произвольного отображаемого имени больше не используется как идентификатор.

Remnawave прежде пропускался полностью. Добавлена проверка по `onlineAt`
в `userTraffic` (с поддержкой старого ответа): активность не старше 2 минут.
Если выбран физический UUID ноды, сверяется `lastConnectedNodeUuid`.
Это оценка последней активности, не точный перечень всех одновременных
соединений: API с последней нодой не описывает все параллельные подключения.
Ошибка API обозначается «Нет данных», а не считается подтверждённым оффлайном.

## Клонирование

В списке/редакторе узла появилась кнопка «Клонировать». Сервер создаёт
выключенную копию сохранённых параметров и открывает редактор. Копируются
подключение, способ авторизации, зашифрованные пароли/токены, inbound ID,
страна, подписи и настройки наследования. Физический UUID/Host Remnawave
сбрасываются. Не копируются клиенты, регистрации агента, статистика,
статусы, кеши и дата создания. Несохранённые правки формы не копируются.

Перед включением копии нужно проверить адрес, inbound или физическую ноду
и Host. Изменения на удалённых серверах при клонировании не отправляются.

## Автовыбор: что исправлено и что нельзя обещать

Он уже использовал Xray Observatory с HTTP-запросом через каждый VPN-outbound,
а не ICMP/TCP ping. Обнаружен принудительный fallback на первый узел при
отсутствии здорового кандидата. Заменён на отдельный blackhole: сначала
дождаться успешной проверки, затем выбирать здоровый узел с меньшей задержкой.
При отсутствии всех ответов новые проксируемые соединения блокируются до
восстановления; намеренные direct-исключения маршрутизации не меняются.

URL проверки теперь должен быть HTTPS. Старый HTTP URL при генерации
заменяется стандартным HTTPS адресом. Проверки параллельные; интервал
сохраняется из настроек профиля. Обновить JSON-подписку и перезапустить VPN
необходимо для получения новой конфигурации.

Проверку выполняет ядро Xray **в клиентском приложении**, потому что
доступность из сети панели и с телефона различается. Проверка одного сайта
не гарантирует доступ ко всем сайтам. В проверенном исходнике Observatory
успех HTTP-запроса не сопровождается строгой проверкой статуса 204. Это
ограничение ядра, не исправляемое произвольным JSON-полем панели.

Переключение возможно для новых соединений после очередной проверки;
уже открытые TCP-соединения не переносятся. Гарантированная смена узла при
каждом переподключении и сохранение списка неудачных попыток на телефоне
в этот выпуск не входят: это требует поддержки приложения/ядра. Работа на
конкретной версии Happ и в сети пользователя пока не подтверждена.

Источники проверки протокола:

- [Xray Observatory](https://xtls.github.io/en/config/observatory.html)
- [Xray leastPing](https://github.com/XTLS/Xray-core/blob/main/app/router/strategy_leastping.go)
- [Реализация HTTP-проверки](https://github.com/XTLS/Xray-core/blob/main/app/observatory/observer.go)
- [Официальная модель ответа Remnawave](https://github.com/remnawave/python-sdk/blob/production/remnawave/models/subscription.py)

## Проверки

- 46 выбранных тестов прошли; 4 Bash-теста пропущены (Bash отсутствует).
- В том числе 10 новых тестов квот, нулевого сброса, отказа API, клонирования,
  Remnawave-online, конфигурации автовыбора и объединения фоновых запросов.
- Изолированный SQLite-тест исполнил сборщик статистики с тестовыми API.
- Скомпилированы 17 EJS-шаблонов; проверен синтаксис изменённого JavaScript.
- Headless Edge: реальные шаблоны с синтетическими клиентами, размеры
  390/1366/1920 px; проверены сочетания узла с онлайн, расходом, исчерпанными
  лимитами, датами, алфавитом и отключёнными клиентами. Горизонтального
  переполнения страницы нет. Проверены живой сброс счётчика и фильтры дашборда.
- Полное приложение с рабочей БД не запускалось. Два дополнительных набора
  тестов не смогли стартовать без better-sqlite3. Полный npm test, Linux/Docker,
  реальный Remnawave/3x-ui и фактическое переключение VPN не проверены.

## Рекомендации — пока не реализованы

1. Разделить внешний счётчик Remnawave-пользователя и физические узлы,
   чтобы исключить повторное суммирование в нескольких привязках.
2. Вынести статистику в отдельный планировщик с временем успешного обновления
   каждого узла/клиента, а не только общей отметкой завершения сбора.
3. Для сложных случаев автовыбора: отдельная диагностика HTTPS через реальный
   VPN-outbound с несколькими адресами, проверкой статуса/содержимого ответа
   и журналом причин исключения. Серверная диагностика не заменит клиентскую.
4. Полная резервная копия БД и конфигурации обязательна: JSON-экспорт проекта
   не является копией всех таблиц. Проверить восстановление на тестовой среде.
5. Разнести крупный app.js и встроенный JS шаблонов по модулям и добавить
   интеграционные тесты именно установленных версий удалённых панелей.

Дополнительные архитектурные изменения и агент не включались.
