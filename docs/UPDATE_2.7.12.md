# Nexus 2.7.12 — Telegram для связи на той же панели 3x-ui

15 октября 2026. Исправление подготовлено локально, на сервер пользователя не устанавливалось и в GitHub не опубликовано. Предыдущие исправления 2.7.8–2.7.11 включены.

## Что исправлено

Раньше служебный узел после окончания подписки требовал другую панель: новый API 3x-ui управляет клиентом глобально, поэтому отдельный inbound с теми же UUID/email мог бы снова включить обычный VPN. Теперь Nexus создаёт отдельную служебную учётную запись (UUID/email/subId) для каждой пары пользователь/служебный узел. Основные UUID, срок, лимит трафика и ссылка Nexus сохраняются.

Разрешено: тот же VPS/IP, та же панель 3x-ui и её порт управления, **другой inbound с отдельным портом подключения**. URL/API Token панели можно оставить прежними. Менять порт управления панелью для этого не нужно. Тот же inbound не допускается. Remnawave с общими аккаунтами по-прежнему требует отдельную панель: просто другой Squad недостаточен.

## Порядок действий

1. Обновить **Nexus**, не установщик `panel-script-v1.sh` и не 3x-ui.
2. В имеющейся 3x-ui создать новый пустой inbound с другим свободным портом, назвать «Telegram для связи». Не копировать в него клиентов обычного inbound.
3. Настроить **серверные** правила Xray для тега только этого inbound: разрешить необходимые назначения Telegram и DNS, затем блокировать остальные назначения. Блокирующее правило должно быть после разрешающих и до общих правил, разрешающих всё. Обычные inbound не затрагивать. Не ставить catch-all direct перед этими ограничениями. Эта версия Nexus не меняет конфигурацию Xray автоматически.
4. В Nexus → Узлы → Добавить выбрать 3x-ui. Указать прежний URL, путь, способ авторизации/API Token, **ID нового inbound** и подпись «Telegram для связи».
5. Включить «Только для истёкших подписок». Импорт клиентов из панели **не включать**. Nexus создаёт отдельные служебные аккаунты всех клиентов в фоне, а не копирует обычные учётные записи. Кнопку массового создания клиентов нажимать не обязательно.
6. В настройках подписки выбрать срок служебного доступа 3/7 дней. Индивидуально: Пользователи → Применить к выбранным → Служебный доступ. Доступен индивидуальный срок/бессрочно.
7. Проверить тестовым клиентом с истёкшим сроком: обновить подписку в приложении, увидеть уведомление о продлении и служебное подключение; обычных узлов быть не должно. Проверить, что Telegram работает, а произвольные сайты через этот inbound — нет. После продления основной подписки служебный аккаунт выключается, обычные узлы снова выдаются.

Ограничение Telegram не равно «только текст»: обычные правила по IP/доменам не умеют надёжно отличить сообщения от фото/видео в зашифрованном трафике Telegram. Требование запретить видео этим обновлением не реализуется. Клиентские правила Nexus/JSON не заменяют серверный запрет: пользователь может их изменить.

## Защита старых данных

- Старые служебные узлы на отдельных панелях продолжают работать без смены ключей. Новые получают независимые аккаунты, сохраняемые до сетевого запроса; повтор и перезапуск не создают новые ключи.
- Обычный узел с уже существующими общими клиентами нельзя просто превратить в служебный на общей панели. При ошибке про старые общие записи добавьте новый пустой inbound как новый служебный узел. Не удаляйте обычный inbound/клиентов ради обхода проверки.
- Не привязывайте аккаунты `nexus-support-…` к обычным inbound вручную. Новый API проверяет UUID/email и подтверждённый список привязок перед обновлением; лишние/неизвестные привязки останавливают операцию, ошибка сохраняется для повторной синхронизации.
- Импорт служебных записей в обычных клиентов запрещён. Снятие служебной роли выключает созданные изолированные аккаунты; они не превращаются автоматически в обычную подписку. Для обычного доступа используйте обычный узел.
- Удалённые клиентские конфиги нельзя отозвать одним скрытием из подписки. Доступ ограничивается сроком/enable аккаунта на сервере; фоновые ошибки синхронизации нужно устранять. Обновление не создаёт Telegram-аккаунт/бота и не публикует WebAdmin SFTPGo.

## Установка

Накопительный архив подходит для Nexus 2.7.7–2.7.11. Сделайте полную резервную копию, включая внешние DATA_DIR/control/workspaces/volumes. На **сервере Nexus** для стандартного Docker-развёртывания:

```bash
unzip Nexus-Panel-2.7.12-shared-panel-support-patch.zip -d /root/nexus-support-2.7.12
cd /root/nexus-support-2.7.12
bash apply-node-traffic-update.sh /opt/3xui-aggregator
```

Вместо `/opt/3xui-aggregator` укажите фактический каталог установки Nexus. Helper запрашивает YES, останавливает только `aggregator`, сохраняет весь каталог в backup рядом и пересобирает этот сервис. Внешние базы/volumes он автоматически не копирует. SQLite добавляет таблицу служебных идентичностей без удаления имеющихся пользователей и узлов. Не накладывайте файлы на работающий процесс.

Для systemd: остановить свой сервис Nexus, сохранить исходники/настройки/все базы, наложить файлы PATCH_FILES.txt с путями, выполнить `npm ci --omit=dev`, запустить сервис. Для отката остановить Nexus и восстановить исходники и базы из полной копии; отдельная замена базы работающего процесса недопустима. Локальный откат сам по себе не отменит созданные/изменённые аккаунты в удалённой 3x-ui.

Публичная команда обновления и `panel-script-v1.sh --update` не устанавливают этот неопубликованный ZIP.

Unit-тесты срока, отключения, продления, сохранения идентичности, совместного URL/разных inbound, отказа при старых общих записях, лишней привязке и импорте. Настоящий HTTP-тест Nexus с фикстурными старым inbound API и новым глобальным Clients API: добавление той же панели, фоновые аккаунты, другой порт, SUB/JSON с отдельным UUID, запрет того же inbound, продление и перезапуск. Для нового API дополнительно: ручная опасная привязка → отказ без включения платного аккаунта → исправление привязки и успешный повтор. Проверки не заменяют тест на боевой 3x-ui и телефоне.

Целевые проверки: 52 pass, 4 platform skip, 0 fail. Синтаксис JS/helper и все 20 EJS проверены. Полный исторический набор сохраняет 10 прежних падений (подробности PROJECT_HANDOFF.md); он не зелёный.
