# Nexus 2.7.15 — direct DNS и routeOnly

21 октября 2026. Локальный накопительный патч для Nexus 2.7.7–2.7.14. Не установлен на сервер пользователя и не опубликован в GitHub. Это обновление **Nexus**, не `panel-script-v1` и не нод.

## Что добавлено

В «Маршрутизация» → «Выбранный через proxy кроме…» рядом с исключениями:

- **Отдельный DNS для исключений → напрямую**. Использует тот же список Domain/GeoSite: `geosite:category-ru`, `domain:qip.ru`, другие введённые домены. IP/GeoIP сам по себе не задаёт DNS: для проверки принадлежности IP его сначала нужно узнать.
- Наборы: Яндекс DoH, Яндекс UDP/53, Cloudflare UDP/53, Google UDP/53 или ручные IPv4/IPv6/HTTPS DoH. Ручные адреса дополняют выбранный набор; «Только вручную» требует хотя бы один адрес. DoT для нового direct DNS не предлагается, поскольку это не универсальный формат Xray DNS.
- Основной DNS остаётся отдельным блоком ниже. Для принудительных proxy-доменов сначала выбирается основной DNS, затем direct-совпадения, затем обычный fallback. При отказе резолвера и пересечении списков fallback может использовать другой путь: это не строгая изоляция DNS от всех альтернативных резолверов.

Отдельный переключатель **routeOnly — только выбирать маршрут, не подменять адрес**:

- выключен: прежнее поведение sniffing, распознанный домен может заменить адрес назначения;
- включён: домен участвует в выборе direct/proxy, но исходный адрес назначения сохраняется;
- не означает «весь трафик напрямую», не включает/выключает весь UDP и не проверяет доступность узла;
- действует только на включённый sniffing в JSON узлов, для которых включена маршрутизация. Для этих узлов Nexus уже включает sniffing при маршрутизации.

Обе новые опции **по умолчанию выключены**, старые настройки не переписываются. Их можно проверять независимо, обновляя JSON и переподключаясь после каждого изменения. Пост из старой открытой формы не сбрасывает новые опции; новая форма явно сохраняет их выключение.

## Как начать проверку

1. Установить обновление Nexus.
2. Открыть «Маршрутизация», выбрать нужные обычные/каскадные узлы режима «через proxy кроме…».
3. В Domain/GeoSite → direct оставить свои исключения, например `geosite:category-ru` и `domain:qip.ru`. Если имелся в виду GeoIP, писать `geoip:ru` в отдельном поле IP/GeoIP, а не `qip.ru`.
4. Включить отдельный DNS, начать с «Яндекс DoH · HTTPS напрямую». Сохранить.
5. Обновить **JSON-ссылку Nexus** в приложении, переподключиться и проверить открытие тех же российских приложений в той же сети, на том же узле. URI/VLESS/SUB не переносят этот JSON DNS.
6. Затем отдельно включить routeOnly, снова обновить JSON и переподключиться. Сравнить результат. Не менять одновременно DNS, транспорт, сервер и UDP: тогда непонятно, что помогло.
7. Повторить на обычной ноде и каскаде. Полного исправления видеозвонков только этой доработкой не обещаем: потери пакетов/задержки и серверные ограничения требуют отдельных измерений.

Выключение direct DNS возвращает прежний основной DNS; выключение routeOnly возвращает прежнее поведение sniffing. Для отката только этих настроек не нужно переустанавливать панель.

## Границы и совместимость

- Серверные профили, входящие UUID/ключи, transport/security/flow, mux и настройки каскада не меняются. Для Remnawave и 3x-ui меняется генерируемый **клиентский JSON**; версии их серверного API здесь не переключаются.
- Direct DNS применяется только к явным Domain/GeoSite исключениям режима `proxy-except`. Не включается автоматически для `node-selective` («выбранное через proxy, остальное напрямую»), исключённых узлов и глобально выключенной маршрутизации.
- У автоподключений DNS proxy направляется через balancer, DNS direct остаётся direct. Ссылки/пароли панели в JSON не добавляются.
- Яндекс DoH использует `https+local://common.dot.dns.yandex.net/dns-query`: запрос DoH идёт вне VPN, начальное определение имени резолвера — через системный DNS устройства. Проверка TLS не отключается. Обычный direct UDP DNS получает отдельный inboundTag и явное routing-правило → direct. Основной не-local DNS при включённой функции явно идёт через proxy/пул.
- Действует на встроенный DNS Xray. Как DNS приложений попадёт в него, зависит от TUN/DNS-перехвата клиента; собственный DoH приложения эта опция принудительно не перехватывает. При routeOnly исходный IP может быть уже известен, и новый DNS-запрос не нужен.
- Нет IP-based DNS выбора по `geoip:ru`, новых функций Lua/новых обязательных настроек Xray и автоматического переключения `IPOnDemand`.
- Неверный direct DNS при сохранении отклоняется до записи и сброса ревизии. Повреждённая настройка из стороннего backup не ломает выдачу HTTP 500: применяется основной DNS, а на странице показано предупреждение.

## Что означает «разрешить UDP»

В присланном обычном профиле SOCKS уже имеет `udp: true`, а финальное правило — `tcp,udp → proxy`. То есть весь UDP не отключён.

Отдельно в клиентском VLESS outbound режим `xtls-rprx-vision` перехватывает **UDP/443**. Поддерживаемый Xray-клиент может проверить вариант `xtls-rprx-vision-udp443` вместо него. Это не повод удалять flow целиком или включать mux.

На каскаде может быть ещё одно ограничение: `mux.xudpProxyUDP443: "reject"` в серверном outbound relay → exit. Изменение только клиентского JSON его не отменит; нужен отдельный тест и явное изменение соответствующего серверного участка. Открытие входящего UDP/443 в firewall само по себе не исправляет передачу UDP внутри VLESS/TCP.

**В этом выпуске UDP/flow/mux не менялись.** Отдельное разрешение UDP/443 не доказывает исправление WhatsApp: видеозвонки нужно проверять по реальному трафику.

Источники: [Xray DNS](https://xtls.github.io/en/config/dns.html), [sniffing / routeOnly](https://xtls.github.io/en/config/inbound.html#sniffingobject), [Vision UDP/443](https://xtls.github.io/en/config/outbounds/vless.html), [Mux/XUDP](https://xtls.github.io/en/config/outbound.html#muxobject), [официальные адреса Яндекс DNS](https://dns.yandex.com/).

## Установка

На **сервере Nexus** сделать полную копию исходников, `.env` и всех баз. Внешние DATA_DIR/control/workspaces/volumes сохранить отдельно. Для существующей Docker-установки:

```bash
unzip Nexus-Panel-2.7.15-routing-dns-patch.zip -d /root/nexus-routing-2.7.15
cd /root/nexus-routing-2.7.15
bash apply-node-traffic-update.sh /opt/3xui-aggregator
```

`/opt/3xui-aggregator` заменить реальным каталогом Nexus. Helper запрашивает YES, останавливает только aggregator, сохраняет полный каталог рядом в backup и пересобирает сервис. Внешние базы автоматически не архивирует. Установка старых ZIP перед этим не требуется.

Для systemd: остановить свой сервис Nexus, сохранить полную копию, перенести файлы по `PATCH_FILES.txt` с сохранением путей, выполнить `npm ci --omit=dev` в каталоге Nexus и запустить свой сервис. Универсальное имя systemd-сервиса не предполагается.

Полный откат: остановить Nexus, восстановить исходники/базы из согласованного backup, пересобрать/запустить сервис. Старые ZIP сохранены. Применение патча временно остановит саму панель; уже скачанные клиентские конфиги обновятся только при обновлении подписки.

`panel-script-v1.sh --update` этот ZIP не устанавливает. Автообновление Nexus тоже не получит неопубликованный локальный архив.
